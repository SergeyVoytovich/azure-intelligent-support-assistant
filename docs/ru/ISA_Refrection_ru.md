# Рефлексия по проекту

## Azure Intelligent Support Assistant

Проект Azure Intelligent Support Assistant оказался для меня полезен прежде всего тем, что объединил в одной работе несколько областей, которые по отдельности выглядят значительно проще: разработку backend и frontend, Azure-инфраструктуру, AI-сервисы, безопасность, CI/CD, тестирование, мониторинг и контроль расходов.

До начала проекта многие из этих компонентов я рассматривал как отдельные технологии. В ходе реализации стало значительно понятнее, как они взаимодействуют в реальном облачном приложении и какие проблемы возникают именно на границах между сервисами.

---

## Что получилось хорошо

Одним из наиболее удачных решений я считаю общую архитектуру приложения.

Backend реализован на .NET 10 и Azure Functions, frontend — на Vue 3 и Azure Static Web Apps. AI-функциональность вынесена в отдельные Azure-сервисы, а backend выполняет их оркестрацию.

Такой подход позволил достаточно чётко разделить ответственности между компонентами и не переносить Azure-специфическую логику во frontend.

Хорошо показала себя и реализация Retrieval-Augmented Generation.

Вместо передачи вопроса напрямую в GPT-4o приложение сначала обращается к Azure AI Search и получает релевантные фрагменты базы знаний. Только после этого найденный контекст передаётся языковой модели.

Использование Hybrid Search оказалось особенно полезным. Комбинация Keyword Search, Vector Search и Semantic Search позволяет находить как точные совпадения, так и тексты с похожим смыслом.

Для обработки документов была реализована собственная ingestion pipeline на .NET:

```text
Blob Storage
→ Document Intelligence
→ Normalization
→ Chunking
→ Embeddings
→ Azure AI Search
```

Это позволило лучше понять весь жизненный цикл данных в RAG-системе, а не ограничиваться использованием готового мастера импорта в Azure Portal.

Ещё одним сильным решением стала автоматизация через Infrastructure as Code.

Инфраструктура была описана с помощью Bicep и разделена на несколько модулей:

```text
core
ai
security
app
budget
web
```

По мере роста проекта это оказалось значительно удобнее, чем управлять всеми ресурсами вручную через Azure Portal.

CI/CD также стал важной частью проекта.

Pipeline автоматически выполняет:

- сборку backend;
- сборку frontend;
- Unit Tests;
- Architecture Tests;
- Frontend Tests;
- проверки зависимостей;
- Gitleaks;
- Trivy;
- Bicep validation;
- создание deployment artifacts;
- автоматический deployment из `dev`.

В результате изменения проходят несколько уровней проверки до того, как оказываются в Azure.

## Основные сложности

Наибольшую сложность в проекте представлял не сам C#-код, а настройка доступа между Azure-сервисами.

Основная идея архитектуры состояла в том, чтобы использовать Managed Identity и Azure RBAC вместо хранения API Keys и Client Secrets.

Концептуально это выглядит достаточно просто, однако на практике оказалось, что для каждого Azure-сервиса необходимо точно понимать:

- какая Identity выполняет запрос;
- к какому ресурсу она обращается;
- какая конкретная роль ей необходима;
- на каком Scope эта роль должна быть назначена.

Особенно много времени потребовала настройка Azure AI Search.

Несмотря на корректно назначенные RBAC-роли, доступ через Microsoft Entra ID сначала не работал. Причина оказалась не только в ролях, но и в конфигурации самого Search Service, где требовалось корректное поведение AAD authentication challenge.

Этот случай был для меня важным уроком: при проблемах авторизации недостаточно проверять только Role Assignments. Необходимо проверять одновременно конфигурацию вызывающего приложения, Identity, RBAC и настройки целевого сервиса.

Кроме того, в процессе настройки возникли временные широкие Role Assignments на уровне Resource Group. После стабилизации приложения они были удалены, а необходимые разрешения оставлены на уровне конкретных ресурсов.

Это позволило привести конфигурацию ближе к принципу Least Privilege.

## CI/CD и Infrastructure as Code

Отдельной сложностью стала необходимость привести уже работающую Azure-инфраструктуру в соответствие с Bicep.

Часть ресурсов и параметров изменялась во время разработки вручную, поскольку необходимо было быстро диагностировать проблемы.

После этого требовалось аккуратно перенести рабочую конфигурацию обратно в Infrastructure as Code так, чтобы следующий deployment не уничтожил или не изменил уже правильно работающие настройки.

Полезным инструментом здесь оказался:

```text
az deployment ... what-if
```

Проверка What-If перед deployment позволяла увидеть, какие ресурсы будут созданы, изменены или удалены.

В дальнейшем я бы использовал такой подход ещё строже: после минимального ручного исправления в Azure сразу переносил бы изменение в Bicep, а не откладывал это до следующего этапа.

## Что я сделал бы иначе

Если бы я начинал проект заново, я бы раньше сформировал окончательную архитектуру Azure-ресурсов и модель доступа.

В частности, ещё до написания основной бизнес-логики я бы подготовил таблицу:

```text
Identity
→ Resource
→ Required Role
→ Scope
```

Это значительно упростило бы работу с Managed Identity и уменьшило количество пробных изменений RBAC.

Также я бы раньше настроил Application Insights, Log Analytics и Alerts.

В этом проекте полноценный monitoring появился ближе к финальной стадии. Он работает и собирает реальные данные, но при более раннем подключении можно было бы анализировать телеметрию в течение всего периода разработки.

Кроме того, я бы раньше зафиксировал различия между схемами KQL в Application Insights и Log Analytics Workspace.

На практике одинаковые данные могут иметь разные имена таблиц и полей в зависимости от того, откуда выполняется запрос. Это небольшая техническая деталь, но она способна отнять заметное время при диагностике.

## Что я узнал о Managed Identity

До проекта Managed Identity выглядела для меня в основном как способ «не хранить пароли».

После практической реализации стало понятно, что её главное преимущество шире.

Managed Identity вместе с Azure RBAC позволяет строить модель доступа, в которой:

- приложение не знает Azure credentials;
- credential rotation не требуется;
- права можно назначать отдельно для каждого ресурса;
- доступ можно централизованно контролировать через Azure.

При этом Managed Identity не устраняет сложность полностью.

Она переносит сложность из управления секретами в правильное управление идентичностями и разрешениями.

На практике это более безопасная модель, но она требует хорошего понимания Azure RBAC.

## Что я узнал о RAG

Работа над проектом также позволила лучше понять ограничения Retrieval-Augmented Generation.

RAG значительно улучшает качество ответов для специализированной базы знаний, однако сам по себе не гарантирует корректный ответ.

Качество результата зависит сразу от нескольких этапов:

```text
Document extraction
→ Chunking
→ Embeddings
→ Retrieval
→ Ranking
→ Prompt
→ Language Model
```

Ошибка или плохая настройка на любом из этих этапов может ухудшить итоговый ответ.

Особенно важным для меня стало понимание того, что RAG — это не просто «подключить GPT к документам», а полноценный информационный pipeline.

Также даже при хорошем Retrieval языковая модель теоретически может сформулировать утверждение, которого непосредственно нет в найденном контексте.

Для реального production-сценария я бы добавил дополнительные механизмы проверки ответа и более строгие правила работы при низкой релевантности найденных документов.

## Тестирование

Положительно оцениваю объём автоматизированного тестирования.

Backend содержит более 150 .NET-тестов, включая Unit Tests, Architecture Tests и Integration Tests.

Frontend также покрыт автоматическими тестами через Vitest.

При этом особенно важным выводом для меня стало различие между Unit Tests и Integration Tests.

Mocked Unit Tests хорошо проверяют собственную бизнес-логику, но не способны гарантировать правильность конфигурации реального Azure-сервиса.

Например, через Unit Test невозможно полностью проверить:

- Azure RBAC;
- Managed Identity;
- Semantic Search configuration;
- реальные model deployments;
- поведение Azure AI Search;
- сетевую и сервисную конфигурацию.

Поэтому для облачных приложений Integration Tests и реальные end-to-end проверки имеют значительно большую ценность, чем в полностью локальном приложении.

## CI/CD и безопасность

Полезным опытом стала настройка Workload Identity Federation для Azure DevOps.

В результате pipeline не требует постоянно действующего Client Secret для Azure deployment.

Вместе с Managed Identity это позволило построить приложение, где и runtime, и CI/CD используют identity-based authentication.

Дополнительные проверки Gitleaks, Trivy, dependency scanning и `npm audit` также показали, что безопасность лучше встраивать непосредственно в pipeline, а не выполнять отдельной ручной проверкой перед сдачей или релизом.

## Мониторинг и эксплуатация

Application Insights и Log Analytics позволили увидеть проект уже не только с точки зрения разработчика, но и с точки зрения эксплуатации.

После настройки стало возможно анализировать реальные:

- Requests;
- Status Codes;
- Response Times;
- Errors;
- Dependencies.

Дополнительно были настроены Alerts для:

- Error Rate > 5%;
- Average Response Time > 3 seconds;
- высокого использования GPT tokens.

Также был создан Dashboard с основными показателями и текущими затратами.

Этот этап показал мне, что завершённое облачное приложение — это не только работающий код. Необходимо также понимать, что происходит с приложением после deployment.

## Контроль расходов

До этого проекта стоимость облачных ресурсов я чаще рассматривал как отдельную административную тему.

Здесь Budget и Cost Management стали частью самого технического решения.

Для проекта установлен месячный Budget в размере:

```text
€30
```

а реальные расходы Development-/Demo-окружения отслеживаются отдельно.

На момент подготовки документации накопленные затраты составляли приблизительно:

```text
US$0.15
```

Этот опыт показал, что стоимость инфраструктуры лучше учитывать одновременно с архитектурой, а не после её реализации.

## Возможное дальнейшее развитие

Для production-версии я бы в первую очередь добавил:

- отдельные Dev-, Test-, Staging- и Production-окружения;
- отдельный Production deployment из `main`;
- пользовательскую аутентификацию;
- Private Endpoints;
- полное отключение локальной API-Key-аутентификации;
- автоматическую синхронизацию и повторную индексацию базы знаний;
- интеграцию с реальной Ticket- или CRM-системой;
- Post-Deployment Smoke Tests;
- End-to-End Tests;
- Load и Performance Tests;
- расширенный мониторинг и Custom Metrics.

Особенно важным следующим шагом была бы реальная эскалация запроса человеку, а не только возврат поля:

```json
{
  "escalationRequired": true
}
```

## Итог

Главный результат проекта для меня заключается не только в создании работающего AI-приложения.

Значительно важнее оказался практический опыт построения целостной Azure-системы, где необходимо одновременно учитывать:

- архитектуру приложения;
- AI;
- данные;
- Identity;
- RBAC;
- Infrastructure as Code;
- CI/CD;
- тестирование;
- безопасность;
- мониторинг;
- стоимость.

Особенно полезными стали практические проблемы с Azure RBAC, Managed Identity и конфигурацией сервисов, потому что именно они показали разницу между теоретическим пониманием Azure и эксплуатацией реальной облачной системы.

В результате проекта я значительно лучше понимаю не только отдельные Azure-сервисы, но и то, как проектировать, развёртывать, диагностировать и сопровождать приложение, состоящее из нескольких взаимосвязанных облачных компонентов.
